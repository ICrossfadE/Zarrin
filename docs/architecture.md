# Архітектура Zarrin

## Зображення через imageUrl — 2026-11-18

Уточнення за реальною відповіддю API: поле Strapi називається `image_url`. `toPost` перетворює його на `Post.imageUrl`; назва UI-поля залишається незмінною. Попередня перевірка imageUrl у сирому JSON пропустила наявне поле через неправильний ключ.

Task/006 замінює `Post.cover` на nullable рядок `Post.imageUrl`. Усі картки Home/Blog/related, featured та обкладинка статті використовують його як `src`. `toPost` нормалізує HTTP(S) URL; для порожнього imageUrl зберігає fallback Post_image.url з абсолютною адресою Strapi. Некоректний URL дає null без втрати списку статей. sortOrder збережено, порядок статей не змінюється.

Файлові Dropbox share links `/s/…` і `/scl/fi/…` отримують `raw=1` замість `dl`, зі збереженням `rlkey` та інших параметрів. Це [офіційний спосіб прямого рендеру](https://help.dropbox.com/share/force-download), що може використовувати redirect. Потрібний публічно доступний файл без входу/пароля. Уже прямі dropboxusercontent URL не переписуються. Dropbox SDK/API та акаунти не додаються.

`next/image unoptimized` передає URL браузеру напряму; серверна оптимізація й remotePatterns не використовуються. Рядок URL не містить alt/розмірів: alt береться із заголовка статті, width/height — із наявних UI-слотів; CSS зберігає responsive crop. Це розміри відображення, а не виміряні метадані файла. Старі описи cover нижче — історія попередньої реалізації.

## Стійкість до недоступної CMS — 2026-11-18

Актуальна поведінка task/005 замінює попереднє передавання помилок у рендер: getPosts() у src/features/blog/blog-posts.ts перехоплює збої запиту, HTTP, JSON і нормалізації, повертає [] та пише нейтральне серверне попередження без URL/секретів. Частковий список при помилці наступної сторінки пагінації відкидається. React cache дедуплікує результат тільки в межах рендеру; наступний запит може відновити дані. fetchAPI лишається строгим і кидає помилки; fallback належить саме читанню статей.

PostsEmptyState — спільний серверний блок «No posts yet» у поточній палітрі; окремого Figma-макета немає. Він замінює лише картки featured/recent/popular на Home і список Blog. Home завжди рендерить оригінальний hero й усі секції; CTA hero без featured веде на /blog. Header отримує [] для пошуку, який одразу пояснює відсутність даних. About/Contact і системна 404 рендеряться незалежно від доступності CMS. Шаблон статті збережений: відсутній у списку slug викликає notFound(), зокрема при порожньому/недоступному списку. Empty state використовує існуючий Reveal, включно з reduced motion і видимим SSR-контентом. Немає автоматичного retry, polling або демо-статей; діє наявний timeout 10 секунд.

## Статті з Strapi — 2026-11-17

За запитом власника локальний масив posts замінено getPosts() у src/features/blog/mock-posts.ts. Назву файлу залишено для сумісності; моків і запиту під час імпорту більше немає. Функція читає всі сторінки API /api/blog-posts, populate Post_image/blog_category, порядок Post_date desc/documentId asc. toPost() перетворює відповідь у незалежний від CMS Post (з id/documentId, nullable cover).

Потрібен запущений Strapi та STRAPI_URL або наявний NEXT_PUBLIC_STRAPI_URL — origin без /api, наприклад http://localhost:1337. Секрети не додаються в Git. HTTP-помилки й таймаут 10 секунд передаються як помилки, без прихованого fallback на демо-дані. Доступ API налаштовується власником; tokens/permissions автоматично не створюються.

У наданому JSON Slug і Post_text = null: URL використовує documentId, стаття показує повідомлення про відсутній текст. Непорожній Post_text наразі підтримується як plain text; Blocks/HTML не інтерпретуються, інший формат потребує окремого узгодження схеми. Відсутні медіа й категорія обробляються без падіння. Для Post_date = null використовується publishedAt.

Home, Blog, пошук, metadata та article читають repository асинхронно. Дані завантажуються під час запиту, не під час build; React cache дедуплікує getPosts у межах рендеру. Невідомий slug повертає 404. Через пошук у спільному Header усі маршрути залежать від доступності Strapi. Featured — перша стаття, recent — перші 3, popular — перші 6; це тимчасова вибірка за датою, не рейтинг популярності CMS.

Зображення CMS мають абсолютні URL та unoptimized у next/image: браузер отримує їх напряму, зокрема з локального Strapi; серверний оптимізатор не потребує дозволу приватних IP. Перед публікацією окремо погодити публічну адресу медіа й оптимізацію. Форми та інші сервіси не змінені. Історичні описи початкової локальної версії нижче зберігаються як попередній етап.


## Стан і межі

Реалізовано локальний frontend: шість типів сторінок, спільні компоненти в `src/components`, локальні статті у `src/features/blog`, GSAP reveal та інертні форми. CMS та зовнішніх сервісів немає. Нижче збережена цільова структура; фактична структура компактніша й не містить порожніх абстракцій.

## Стек

- Next.js App Router: маршрутизація, серверний рендеринг і metadata.
- React + TypeScript strict: типізація даних і компонентів.
- Tailwind CSS через PostCSS: стилі та майбутні дизайн-токени у `@theme`.
- GSAP + ScrollTrigger: reveal секцій через `components/reveal.tsx`, `gsap.matchMedia` та cleanup.
- Raleway і Roboto: локальні OFL-шрифти з пакетів Fontsource, завантажуються через `next/font/local`.
- npm та package-lock.json: відтворюване встановлення. ESLint і TypeScript: статичні перевірки.

Конкретні встановлені версії — у package.json і lockfile. Сторонні UI-бібліотеки для цього макета наразі не потрібні.

## Цільова структура (створюється поетапно)

```text
src/
  app/
    layout.tsx                 # metadata, глобальні стилі
    page.tsx                   # Home: /
    blog/page.tsx              # Blog: /blog
    blog/[slug]/page.tsx       # один шаблон для всіх статей
    about/page.tsx             # /about
    contact/page.tsx           # /contact
    not-found.tsx              # системна 404
  components/
    layout/                    # Header, Footer, mobile navigation
    ui/                        # Button, Container, Section, поля
    blog/                      # BlogCard, BlogGrid, ArticleContent
    sections/                  # секції конкретних сторінок
    motion/                    # клієнтська межа Reveal
  features/blog/
    types.ts                   # незалежна від CMS модель
    repository.ts              # список і пошук за slug
    mock-posts.ts              # локальні демонстраційні статті
  lib/                       # лише реальні спільні утиліти
public/
  images/                    # локальні оптимізовані assets
  fonts/                     # після перевірки шрифтів і ліцензій
docs/
task/
AGENTS.md
```

Не створювати порожні абстракції наперед. Розділяти компоненти, коли є повторення або окрема відповідальність.

## Дані блогу та майбутня CMS

Реалізовано 10 локальних статей у `mock-posts.ts` з перевіркою `satisfies Post[]` та типи `Post`, `Picture`, `ContentBlock`. Одна містить текст шаблону Figma, дев'ять — короткий демонстраційний контент із карток. UI звертається до `listPosts()` та `getPostBySlug(slug)` через repository. Усі slug пререндеряться `generateStaticParams`, невідомі повертають 404. Автор, SEO-поля та розширена модель CMS нижче є планом, не виконаними можливостями.

Цільова модель Post: id, slug, title, excerpt, cover (src, alt, width, height), category, author, publishedAt (ISO), body (типізовані блоки тексту, заголовків, зображень і цитат), SEO title/description. Категорії та автори можуть бути окремими моделями при підключенні CMS.

Після погодження CMS замінюється реалізація repository; UI лишається незалежним від SDK провайдера. Валідація зовнішнього контенту відбувається на сервері, секрети не мають префікса NEXT_PUBLIC. Для оновлення публікацій окремо визначити стратегію кешу, preview/draft та захищеної revalidation. Зараз жодних SDK, API routes, БД або webhook немає.

## Рендеринг і анімації

Сторінки, статті та завантаження даних — Server Components. Клієнтські компоненти потрібні для mobile menu, локальних UI-станів і GSAP. Reveal використовує refs, ізольований GSAP context, cleanup при unmount та навігації. ScrollTrigger реєструється лише на клієнті. Для reduced motion анімації вимкнені; базовий CSS залишає контент видимим без JS.

## Дизайн і адаптивність

Style Guide та макети прочитано через настільну програму; підтверджені значення й інженерні рішення розмежовані у [design-audit.md](design-audit.md). Сітки fluid, адаптивні правила охоплюють desktop, tablet і mobile. Контент залишається видимим без JS; лише пошук, автоматичне закриття мобільного меню та reveal потребують клієнтського коду.

Кожен інтерактивний елемент має pointer, hover, transition і видимий keyboard focus. Семантичні посилання для навігації, кнопки для дій. Контактна форма та підписка тільки візуальні: без надсилання й збереження даних, без submit і повідомлень про вигаданий успіх. Пошук, фільтри й пагінацію реалізовувати лише коли їх наявність та поведінку підтверджено.

## Якість і підготовка до релізу

ESLint, TypeScript і production build для змін коду. Для реалізованих сторінок: візуальне порівняння з Figma, 360/390/768/1024/1440 px і проміжні ширини, відсутність горизонтального скролу, keyboard/mobile navigation, reduced motion, 404, переходи, відсутність мережевих запитів форм. Автоматичні тести додавати для значущої поведінки, а не для технічної заглушки.

До публікації: page metadata, canonical, Open Graph, sitemap, robots та Article structured data на справжньому контенті; фінальний домен потрібен для абсолютних URL. Оптимізація локальних зображень через next/image, перевірка LCP/CLS, доступності та ліцензій. Інфраструктурні рішення окремо описані у services.md і потребують згоди.
