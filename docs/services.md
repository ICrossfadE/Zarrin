# Сервіси для завершення проєкту

Стан: **нічого не підключено**. Нижче — рекомендації, а не затверджений стек. Без згоди власника не створювати акаунти, проєкти, DNS-записи, інтеграції, SDK або платні підписки. Тарифи й ліміти потрібно перевірити перед вибором; бюджет не задано.

## Що потрібно до публічного запуску

| Потреба | Пропозиція | Навіщо / умови |
| --- | --- | --- |
| Хостинг Next.js | Vercel або власний Node.js-сервер | Публікація сайту й HTTPS. Vercel — рекомендований для розгляду варіант завдяки інтеграції з Next.js; власний сервер потребує оновлень, TLS, reverse proxy й резервного копіювання. [Документація](https://vercel.com/docs/frameworks/full-stack/nextjs). |
| Домен і DNS | Реєстратор на вибір; Cloudflare DNS як варіант | Власна адреса сайту та DNS-записи. Cloudflare не замінює хостинг; окремий проксі/CDN або WAF оцінювати після вибору хостингу. [Cloudflare DNS](https://developers.cloudflare.com/dns/), [довідка інфраструктури й безпеки](https://developers.cloudflare.com/fundamentals/reference/). |
| Редагування CMS-блогу | Sanity або Payload, обрати один | Sanity варто розглянути для керованого контентного середовища; Payload — якщо потрібний контроль над розгортанням. Для self-hosted CMS окремо визначити БД, медіасховище, доступи й операційне обслуговування. [Sanity](https://www.sanity.io/docs), [Payload](https://payloadcms.com/docs/getting-started/what-is-payload). |
| Резервні копії | Механізм обраної CMS/БД і медіасховища | Зберігати контент та assets, узгодити частоту, термін зберігання й перевірку відновлення. Локальні демонстраційні статті поки зберігатимуться в коді. |

Моя пропозиція для обговорення: Next.js на Vercel + домен + керована CMS Sanity. Cloudflare DNS — за потреби управління доменом; проксі та WAF додавати за конкретними вимогами. Це інженерна рекомендація, остаточний вибір залежить від бюджету, кількості редакторів, обсягів контенту та бажаного контролю.

## Корисно, але не обов'язково для першої версії

| Потреба | Що розглянути | Для чого |
| --- | --- | --- |
| Помилки та доступність | Sentry, окрема uptime-перевірка або можливості хостингу | Виявляти помилки й недоступність після релізу. Для моніторингу погодити, які дані передаються. [Sentry для Next.js](https://docs.sentry.io/platforms/javascript/guides/nextjs/). |
| Репозиторій і CI | Git-хостинг на вибір + pipeline lint/typecheck/build | Історія змін і перевірки перед релізом. Локальний Git поки не ініціалізований; remote не створено. |
| Аналітика | Обрати після визначення метрик і вимог приватності | Оцінювати трафік і читання статей. Не є умовою працездатності сайту, зараз не встановлювати. |

## Що зараз не потрібно

- Поштовий провайдер, newsletter-сервіс, CRM, CAPTCHA: усі форми за вимогою інертні. Підключення можливе лише після явної зміни цієї вимоги.
- Окрема БД для frontend-шаблонів: локальних даних достатньо. БД може знадобитися обраній CMS.
- Авторизація читачів, коментарі, платежі, зовнішній пошук: цих вимог немає.
- Окремий image CDN до вибору CMS/хостингу: спочатку оцінити їхні можливості.

## Чого ще бракує поза сервісами

Доступу до style guide та assets Figma, реального контенту, підтвердженої мови, контактів і соціальних URL, правил редакторської роботи, ліцензій на медіа та SEO-даних. Перед запуском потрібні адаптивна й accessibility-перевірка та рішення щодо домену. Приватність і юридичні тексти слід визначити відповідно до реально зібраних даних та інтеграцій.
