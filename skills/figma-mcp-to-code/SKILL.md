# Figma MCP → код проєкту

Відтворюй погоджений дизайн у стеку поточного проєкту. Читай Figma через доступний MCP-конектор; не змінюй сам файл Figma. Ця навичка не встановлює сервер, не надає авторизацію та не підключає зовнішні сервіси.

## Підготовка й межі роботи

- Прочитай AGENTS.md та вкладені інструкції, README, архітектуру, план, конфігурації й наявний код у потрібному обсязі. Якщо локальні правила вимагають читання всіх авторських файлів — виконай це. Не виводь секрети та не читай згенеровані каталоги як авторський код.
- Уточни обсяг із запиту та контексту: конкретні frames, сторінки або компоненти. Запит створити/оновити цю навичку не дозволяє починати верстку.
- Перед змінами створи або продовж відповідну задачу в `task`, коли цього вимагає проєкт. Запиши обсяг, план, критерії та перевірки. Зберігай чужі зміни.
- Знайди готові компоненти, дизайн-токени, шрифти, assets і залежності проєкту. Визнач стек за конфігураціями, не нав'язуй новий.

## Спочатку перевір MCP

1. Відкрий доступні інструменти за назвою та описом: Figma, design context, screenshot, metadata, variables, Code Connect. Коли є `ALL_TOOLS`, відфільтруй його. Відрізняй інструкцію skill від реально доступного конектора: наявність SKILL.md не доводить наявність MCP.
2. Перевір схеми знайдених інструментів перед викликом. Назви та параметри залежать від сервера; не вигадуй namespace, endpoint, аргументи чи результат виконання.
3. Якщо доступна офіційна навичка `figma-design-to-code`, прочитай її перед `get_design_context` і виконуй її вимоги. Зокрема, для конектора з `skillNames` додай `figma-design-to-code`; префікс `resource:` потрібний лише для навички, завантаженої як MCP resource.
4. Виконай читання цільового node, щоб перевірити фактичний доступ. У разі помилки розрізняй: інструмент відсутній, потрібна авторизація, файл недоступний, node не знайдено, ліміт або неповна відповідь. Повідомляй лише підтверджену причину й потрібний наступний крок.
5. Якщо інструментів немає, перевір доступні засоби discovery плагінів за правилами середовища. Не встановлюй і не авторизуй інтеграцію без дозволу. Не роби висновок про приватність файлу з помилки вебінструмента.

Якщо MCP-контекст отримати неможливо, продовжуй лише незалежну підготовку в межах запиту. Не починай верстку «за Figma» на вигаданих параметрах. Поясни конкретний блокер і попроси відсутній доступ, коли він необхідний. Вебсторінка Figma або браузерний скриншот не замінює структурований MCP-контекст; альтернативний режим реалізації погоджуй з користувачем.

## Збери контекст дизайну

- Витягни file key та node-id з посилання. Наприклад `node-id=401-1400` відповідає `401:1400` для API, що очікує такий формат; дотримуйся схеми конкретного інструмента. Якщо node не задано, знайди потрібні frames через metadata; став питання лише за істотної неоднозначності.
- Отримай високодетальний design context цільового frame та його screenshot. Запроси screenshot у першому виклику, якщо API це підтримує; якщо він не повернувся, окремо отримай його до редагування UI.
- Sparse або обрізана відповідь недостатня: зістав child node IDs зі скриншотом і дочитай видимі секції/компоненти. Незалежні читання групуй; не повторюй без змін запити, що вже завершилися однаковою помилкою.
- Прочитай desktop і mobile frames, style guide, стилі/variables та variants, які визначають потрібний UI. Відокрем підтверджені токени від припущень; не називай підібраний колір чи шрифт значенням Figma.
- Збережи в задачі або наявному design-документі відповідність `сторінка → node → маршрут`, перевірені токени, assets і відсутні стани. Не дублюй великі MCP-відповіді без потреби.
- Якщо є Code Connect, використовуй відповідний компонент у mapped node; не відтворюй його заново без обґрунтованої несумісності.

## Assets та реалізація

- Використовуй точні статичні assets і їхні місця з дизайну або ідентичні локальні відповідники. Завантажуй їх способом, указаним MCP-відповіддю та навичкою конектора. Не лишай у коді тимчасові Figma URL або localhost URL сервера assets. Скриншот екрана — візуальний еталон, не фон чи заміна інтерфейсу.
- Перевір непорожні файли, формат, intrinsic dimensions, crop, aspect ratio та місце використання. Не перемальовуй SVG і не замінюй фото випадковими. Для наданих SVG зберігай root dimensions, якщо конектор вимагає цього; уникай глобального розтягування всіх SVG.
- Перенеси контекст у наявну архітектуру: повторно використовувані компоненти й токени, semantic HTML, grid/flex, типізовані props/дані. Згенерований MCP-код — джерело контексту, яке потрібно адаптувати; не копіюй зайві залежності чи абсолютне позиціювання всієї сторінки.
- Реалізуй responsive-поведінку за desktop/mobile frames. Для відсутніх mobile-станів виведи поведінку зі спільної системи й запиши припущення. Зберігай порядок читання та працездатність на проміжних ширинах.
- Навігація — посилання, дії — кнопки; передбач keyboard focus, доступні labels/alt. Hover, transition, pointer та анімації додавай відповідно до вимог проєкту. Не вигадуй destinations або бізнес-логіку, яких немає в запиті.

## Якщо поточний проєкт — Zarrin

Читай `docs/figma.md`, `docs/architecture.md`, `docs/plan.md` та AGENTS.md; вони визначають актуальний обсяг. Під час погодженої реалізації використовуй Next.js App Router, TypeScript strict і Tailwind; Server Components за замовчуванням. GSAP reveal усіх секцій із cleanup і `prefers-reduced-motion`; контент видимий без JavaScript. Усі інтерактивні елементи мають pointer, hover, transitions і focus-visible.

Форми тільки візуальні: без submit, відправлень, збереження, API або вигаданого success state. Спочатку локальні типізовані статті через спільний шаблон. CMS, хостинг, DNS, аналітику та інші сервіси не підключай без згоди. Залишай українські коментарі для власника біля нетривіальних рішень і припущень.

## Перевір результат

- Виконай перевірки, визначені проєктом; для Zarrin — lint, typecheck і production build. Не додавай тести, що лише повторюють розмітку.
- Запусти застосунок, відкрий цільовий маршрут у браузері й порівняй з Figma screenshot при однаковій ширині viewport. Перевір desktop, mobile та проміжні ширини, типографіку, перенесення тексту, відступи, колір, assets і crop. Для порівняння reveal дочекайся кінцевого видимого стану або ввімкни reduced motion.
- Перевір кожен видимий статичний asset: локальний файл, відповідність шару, callsite та фактичну геометрію. Виправляй розбіжності в погодженому обсязі; сторонні розбіжності лише зазначай.
- Перевір клавіатуру, hover/focus, mobile navigation, overflow, помилки консолі та анімації при повторній навігації. Для інертних форм перевір відсутність запитів і передачі полів у URL.
- Заверши задачу з результатами перевірок і невирішеними питаннями. Якщо не було MCP-доступу, assets або браузерної перевірки, явно вкажи це; не стверджуй точну відповідність макету без доказів.

У відповіді назви реалізовані маршрути/компоненти, джерела Figma, перевірки й матеріальні обмеження. Навичка вважається застосованою успішно, коли результат підтверджено контекстом MCP та перевіркою інтерфейсу, а не лише фактом генерації коду.
